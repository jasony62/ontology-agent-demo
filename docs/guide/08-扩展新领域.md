# 08 把本体服务变成你自己的
> 本文是《本体上手指南》系列第 9 篇（共 9 篇），零基础入门「本体 × 智能体」。

> 阅读时长：约 12 分钟 · 配套动手：约 15 分钟
> **读完你能**：换掉示例本体、新建自己的领域、加自己的规则与查询——从"会用"到"能造"

---

## 三条扩展路径

前 7 篇你都在"用"示例本体（智能体任务编排）。这一篇讲"造"：把这套能力变成你自己的。按改动量从小到大，有三条路径：

![把本体服务变成你自己的：三条扩展路径](assets/08-extend.png)

| 路径 | 场景 | 改动量 |
|---|---|---|
| **A 换同构本体** | 业务结构相似，只是类名/属性名不同 | 最小：改配置，不改代码 |
| **B 新建领域** | 完全不同的业务 | 中：拷贝模板，核心零改动 |
| **C 加规则/查询** | 在现有领域上增量扩展 | 小-中：三处联动 |

**共同前提**：核心层（reasoner/）零领域词汇——所以无论怎么扩展，引擎、API、MCP、CLI 都不用改。

## 路径 A：换一个同构本体（实测）

假设你的业务叫"工人-工作"：类叫 Worker/Job/Pipeline，属性叫 owns_skill/needs_skill，但结构（谁有技能、任务要什么技能、复合任务由子任务组成）和示例本体一模一样。

只需要两步配置。在容器内跑（容器已含全部代码与依赖，`-T` 关闭 TTY 以支持管道输入）：

```bash
docker compose exec -T api python - <<'EOF'
from reasoner.engine import OntologyEngine
from domains.agent_task import DEFAULT_CONFIG

# 0. 构造最小"工人-工作"同构本体（类/属性名不同，公理结构保留）
owl = '''<?xml version="1.0"?>
<rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
         xmlns:owl="http://www.w3.org/2002/07/owl#"
         xmlns="http://ontology.localhost/worker-job#">
  <owl:Class rdf:about="http://ontology.localhost/worker-job#Worker"/>
  <owl:Class rdf:about="http://ontology.localhost/worker-job#Job"/>
  <owl:Class rdf:about="http://ontology.localhost/worker-job#Pipeline"/>
  <owl:Class rdf:about="http://ontology.localhost/worker-job#Coding"/>
  <owl:ObjectProperty rdf:about="http://ontology.localhost/worker-job#owns_skill"/>
  <owl:ObjectProperty rdf:about="http://ontology.localhost/worker-job#needs_skill"/>
  <owl:ObjectProperty rdf:about="http://ontology.localhost/worker-job#part_of"/>
  <rdf:Description rdf:about="http://ontology.localhost/worker-job#worker_a">
    <rdf:type rdf:resource="http://ontology.localhost/worker-job#Worker"/>
    <owns_skill rdf:resource="http://ontology.localhost/worker-job#Coding"/>
  </rdf:Description>
  <rdf:Description rdf:about="http://ontology.localhost/worker-job#job_x">
    <rdf:type rdf:resource="http://ontology.localhost/worker-job#Job"/>
    <needs_skill rdf:resource="http://ontology.localhost/worker-job#Coding"/>
  </rdf:Description>
  <rdf:Description rdf:about="http://ontology.localhost/worker-job#pipe_p">
    <rdf:type rdf:resource="http://ontology.localhost/worker-job#Pipeline"/>
    <part_of rdf:resource="http://ontology.localhost/worker-job#job_x"/>
  </rdf:Description>
</rdf:RDF>'''
open("/tmp/worker_job.owl", "w").write(owl)

# 1. 加载新本体，必须传命名空间！
eng = OntologyEngine("/tmp/worker_job.owl", ns="http://ontology.localhost/worker-job#")

# 2. 覆盖类角色映射，领域查询原样复用（经 SDK 上下文 + 领域唯一工厂）
from ontology_plugin_sdk import PluginContext
from domains.agent_task import create_adapter_ctx
ctx = PluginContext.for_engine(eng, config=DEFAULT_CONFIG.update(
    agent_class="Worker", task_class="Job", complex_task_class="Pipeline",
    has_capability="owns_skill", requires_capability="needs_skill"))
adapter = create_adapter_ctx(ctx)

print("agents():", [a.split('#')[-1] for a in adapter.agents()])
print("tasks():", [t.split('#')[-1] for t in adapter.tasks()])
print("复合任务识别 pipe_p:", adapter.is_complex_task(adapter.NS["pipe_p"]))
EOF
```

**这段 XML 在说什么**（读者第一次"手写"本体，逐块对照）：

| 代码块 | 作用 | 对应知识 |
|---|---|---|
| `<rdf:RDF ... xmlns="http://ontology.localhost/worker-job#">` | 文件根 + 命名空间：本文件所有无前缀的名字都归这个 IRI 管 | 篇 1 的 IRI 概念 |
| `<owl:Class rdf:about="...#Worker"/>`（3 行） | 声明 3 个类：Worker、Job、Pipeline；`/>` 是"没有内容"的自闭合标签 | 篇 1 的 `owl:Class` |
| `<owl:ObjectProperty rdf:about="...#owns_skill"/>`（3 行） | 声明 3 个对象属性：owns_skill、needs_skill、part_of | 篇 3 的 `ObjectProperty` |
| `<rdf:Description rdf:about="...#worker_a">` | 声明一个**个体**（这里没有用 owl:NamedIndividual，rdf:Description 是更通用的写法） | 篇 1 的"个体" |
| `<rdf:type rdf:resource="...#Worker"/>` | 声明这个个体**是 Worker 类的一员**（"是一个"） | 篇 1 附录的 `rdf:type` |
| `<owns_skill rdf:resource="...#Coding"/>` | 给个体加一条关系：worker_a 具备 Coding 能力。**不带前缀的属性名**默认属于本文件命名空间 | 篇 1 的三元组 |

整段 XML 产生的关键三元组：`worker_a rdf:type Worker`、`worker_a owns_skill Coding`、`job_x needs_skill Coding`、`pipe_p part_of job_x`——用篇 1 学过的读法，这段就完全可读了。

实测结果（最小同构本体，上脚本容器内输出）：

```text
agents(): ['worker_a']              # Worker 类的个体
tasks():  ['job_x']                 # Job 类的个体
复合任务识别 pipe_p: True           # Pipeline 类被识别为复合任务
classify 新个体 job_y: 正常分类      # 新增/分类能力照常工作
```

**两个关键点（都是实测踩出来的）**：

1. **必须传 `ns` 参数**。引擎的默认命名空间是示例本体的（`agent-task-ontology#`），不传的话，`Worker` 会被解析成示例本体的命名空间下，查不到任何个体——表现为 `agents()` 静默返回空。**换本体第一件事：确认命名空间并传入**。
2. **公理结构必须保留，R1/R2 落在规则层、R4 落在校验代码**。R3 传递闭包这类推理规则活在**本体公理**里，新本体保留同样结构即可自动复用；R1 能力匹配（任务要求的每项能力 Agent 都具备 ⇒ 可执行，AND 全覆盖）与 R2 的组合语义（整体由各部分组成、能做全部部分 ⇒ 能做整体）写成 `rules/*.ttl` 的 SHACL 规则——**不让 .owl 因"每智能体一条组合公理"而膨胀**，也不写成一次性 Python 遍历（没有不动点，会因个体排序漏推）；R1 尤其不能用属性链公理表达（`has_capability ◦ required_by ⊑ can_execute` 是逐条 OR 蕴含，多能力任务只满足一项即误判可执行，#59）；R4 是运行时校验（不产出新事实），留在适配器代码里。换领域时这套分层照搬：能推结论的规则进规则层，校验进代码，但**该不该为你的新领域写类似的组合规则，取决于业务是否真的需要这种聚合语义**（见路径 C）。

## 路径 B：新建一个领域（九步）

业务异构时（比如从"任务编排"换到"供应链风险"），新建领域包。按 DESIGN.md 的约定，**新增一个领域 = 在运行态 root（默认 `domains/`）下新建一个自包含目录，暴露约定符号，引擎/API/MCP/CLI 全部复用，零改动**：

```
<运行态 root>/<name>/
├── __init__.py            # 纯导出：转发 adapter / mcp 的符号
├── adapter.py             # 业务逻辑（必暴露 NAME/DESCRIPTION/ONTO_FILE/create_adapter_ctx）
├── config.json            # 领域语义配置（类角色映射；可声明 onto_file）
├── guide.json             # 使用视角说明（契约必填：定位 / 覆盖 / 能力用途 / 示例题 / 接入）
├── derivation.json        # 推导链配置（文案 + 展开规则）
├── mcp.py                 # 领域 MCP 工具注册（可选，有则自动加载）
└── <name>_ontology.owl    # 本体定义（Protege 可编辑）
```

> 路径说明：随仓库分发的示例在 `examples/`，**不直接生效**；`domains/` 是运行态 root（已进 `.gitignore`，由安装命令重建）。加载位置与默认领域由 `config/domain.json` 决定，优先级 CLI > 环境变量（`ONTOLOGY_DOMAINS_ROOT` / `ONTOLOGY_DOMAIN`）> 配置文件 > 模板 > 内置默认。

九步流程：

1. 选一个起点：
   - **从零起步（推荐先试这个）**：复制 `examples/_minimal/` —— 一个 owl（1 类 3 个体）+ 4 行
     `config.json` + 一个只继承 `AdapterBase`、不写任何业务方法的适配器。它能加载、能出图谱、
     能过契约校验，用来确认"框架这条路走得通"再往上加业务；
   - **形状和 agent_task 对不上时，先想清楚能力清单**：若你的领域不需要
     `capability_match` / `orchestrate` / `assign`，在 `CAPABILITIES` 里把这些能力显式排除即可，
     不必为了满足契约硬写空方法；声明为 `()` 则是合法的"零能力"领域；
   - **照完整示例改**：复制 `examples/agent_task/`（12 个文件、带业务规则与 MCP 工具）；
   - 也可以用安装命令一步就位：`python scripts/ontologyctl.py domain install --from ./examples/agent_task`（把示例装进运行态，再在其上改）。
   注意新领域的适配器只应 import `ontology_plugin_sdk`（领域插件 SDK，见 `packages/ontology-plugin-sdk/`）
   与 `rdflib`；不要 import `reasoner.engine` / `reasoner.semantic` 等宿主内部模块——有测试守着这条边界。
   SDK 不依赖宿主，所以你的领域包拷到仓库外、只装 SDK 也能跑——`tests/test_sdk.py` 里那条
   "脱离仓库"用例就是这么验证的（复制 SDK 与示例包到临时目录，摘掉全部仓库源码路径后起子进程）；
2. 替换本体 `.owl`（用 Protege 建模，**中文名统一放 `rdfs:label`**——它是中文名的唯一事实源）；若包内有多个 `.owl`，在 `config.json` 里用 `"onto_file"` 显式声明核心本体；
3. 改 `config.json` 的类角色映射与结构数据；
4. 改 `derivation.json` 的文案与展开规则；
5. 重写 `adapter.py` 的查询方法（引擎原语 + 你的业务规则），暴露 `NAME/DESCRIPTION/ONTO_FILE`；
   同时补齐 `guide.json`（`GUIDE_FILE` 缺省即该文件）：它是**契约必填**，加载期与安装期都校验；
   字段表、三条规则与最小样例见本节末尾「guide.json 字段表」。
   `CAPABILITIES` 里写**你的领域真正提供**的能力——既可以是框架既有的名字，也可以是
   你自己的（如 `diagnose`）。**声明即承诺**：清单里每个名字都得有落点，否则加载就被拒。
   框架不要求你实现 `diagnose`（它无从知道异构领域该有什么），但要求这个名字至少能被到达——
   落在契约方法、`QUERY_HANDLERS`（只读）或 `APPLY_HANDLERS`（变更）的处理器、或适配器同名方法三者之一；
6. （可选）写 `mcp.py` 注册该领域的 MCP 工具（供智能体调用）；SHACL 形状文件用包内 `SHAPES_FILE` 声明或 `ONTOLOGY_SHAPES_FILE` 指定。
   **想让领域自有能力也走 REST**，在适配器上补一张出口表即可，不用改框架：

   ```python
   def _handle_diagnose(adapter, req):
       # 公开参数名与适配器方法/返回字段一致
       component = (req.params or {}).get("component")
       if not component:
           raise ValueError("diagnose 需要 component")   # → HTTP 400
       return adapter.diagnose(adapter.NS[component])

   QUERY_HANDLERS = {"diagnose": _handle_diagnose}   # 只读能力挂这张；会改图的挂 APPLY_HANDLERS
   ```

   处理器签名与框架内置表一致 `(adapter, request) -> dict`，领域参数从 `request.params` 取；
   抛 `ValueError` 会被转成 400（领域包不必为了状态码 import FastAPI）。之后
   `POST /api/domains/current/capabilities/query {"kind": "diagnose", "params": {"component": "pump_01"}}` 即可触达，
   `/api/health` 的 `contract.query_kinds` 会列出当前领域所有可调只读能力（写能力看 `apply_kinds`）。
   同一能力名不得同时注册进两张表——加载期直接拒绝。
   不注册处理器也行——只写同名方法意味着"只有 MCP 出口"，加载同样放行；
   能力端点对内置与领域能力一视同仁：请求顶层只有 `kind` / `params` / `persist`，
   参数一律进 `params`，框架不为任何领域把 `task` / `agent` 之类的键钉进请求模型。
7. 让领域支持 `POST /api/domains/current/entities`（新建实体）：声明 `ENTITY_SCHEMA`，字段名与类型**由你的领域决定**。

   契约只要求 `create(payload)`，实体形状交回领域、由 `ENTITY_SCHEMA` 描述：

   ```python
   ENTITY_SCHEMA = {
       "class": "fault_class",          # 语义配置键或本体短名（走 config.resolve）
       "id_field": "name",              # 个体 IRI 取自哪个字段（必填）
       "label_field": "label",          # 可选：写 rdfs:label
       "fields": [
           {"name": "name", "kind": "literal", "type": "str"},
           {"name": "label", "kind": "literal", "type": "str"},
           {"name": "severity", "property": "hasSeverity",
            "kind": "literal", "type": "int", "required": True},
           {"name": "remedies", "property": "hasRemedy",
            "kind": "node", "many": True},
       ],
   }
   ```

   - `kind`：`literal` 写数据属性，`node` 写对象属性（取值是本体短名，**必须已存在**，否则拒绝写入）；
   - `type`：`str` / `int` / `float` / `bool`，用于把 `"4"` 这类字符串归一成数字；
   - 继承 `AdapterBase` 就白拿默认实现，**一行代码都不用写**；需要富返回时覆盖 `create`，
     但请先调 `normalize_entity_payload(self, payload)` 复用框架校验，规则只有一份。

   校验分两层，都发生在你会看见的地方：**加载期**拒掉写错的 schema（字段无名 / 重名 /
   `kind` 拼错 / `id_field` 指向不存在的字段），**请求期**拒掉未知字段（把字段名拼错当成
   "生效了"是最难查的一类问题）、缺必填、类型不符、悬空引用——一律 400。
   `GET /api/domains/current/entities/schema` 会把你声明的形状原样吐出来，集成方据此构造 payload。
   典型用法是让推理承担定级：把等级写成 `owl:hasValue` 约束，创建时只填数值，
   分类由推理得出，领域代码零参与；
8. 让图谱按你的领域分组上色：在 `config.json` 的类角色映射旁边声明 `graph_groups`（组名 → 类键）。

   ```json
   "graph_groups": {
     "Equipment": "equipment_class",
     "Component": "component_class",
     "Symptom": "symptom_class",
     "FaultMode": "fault_class",
     "Remedy": "remedy_class"
   }
   ```

   组的**成员按子类收全**（`Pump ⊑ Equipment` 的个体会归进 `Equipment` 组），所以
   类层次写得越细，配置反而越省。书写顺序就是图例顺序，不要指望字典序替你排。
   成员为空的分组不进图例——摆一个 0 项分组只会让人以为图漏渲染了。

   声明之后 `/api/domains/current/ontology/graph-groups` 会把它报出来，前端据此给节点上色并出图例；
   **配色由前端从固定调色板按声明顺序取**，领域不必也不该写色值（那会把主题耦合进
   业务配置）。不声明这项也能跑，图回落到「类一种色、个体一种色」。

   ⚠️ 不要在 `graph_export` 里手写 `"group": "Agent"` 这类字符串——那是把列名
   复制成两份，配置里加一组会被静默丢掉，而前端图例读的是配置，两边会慢慢漂。
   确实需要给某组加展示字段时，用 `graph_group_members(self)` 拿分组与成员，
   再按组名登记字段（见 `examples/agent_task/adapter.py` 的 `_group_row`）；
9. 验证：`ontologyctl domain list` 出现新领域 → `load_domain("name", engine)` 能加载 → `mcp/mcp_server.py --domain name` 自动切换领域工具；REST API 侧切换默认领域可改 `config/domain.json` 的 `domains.default`（或 `ONTOLOGY_DOMAIN`）重启生效；运行时也支持热切换——`POST /api/domains/{name}/activate` 立即切到另一个已安装领域，`POST /api/domains/reload` 重载领域代码，都不必重启（详见管理器的 L1/L2/L3 三级：本体内容 / 同包代码 / 跨包）。

注意第 3–4 步和 `adapter.py` 的职责分工：**配置管"语义映射"，代码管"业务逻辑"**。绝大多数"换个说法"（类名、属性名、展示文案）动配置即可。

### guide.json 字段表（第 5 步）

`guide.json` 是**契约文件**，不是帮助文档：包在 `__init__.py` 声明 `GUIDE_FILE`（缺省 `guide.json`），加载期与安装期都会校验，不合格就**整包拒绝**，不降级成空态。

| 槽位 | 类型 | 规则 | 说明 |
|---|---|---|---|
| `guide_version` | string | 必填，当前只认 `"1"` | 说明文件格式号；与 `PLUGIN_API` 独立演进 |
| `display_name` | string | 必填非空 | 「当前领域」页标题上的中文包名 |
| `summary` | string | 必填非空 | 一句话定位 |
| `scenarios` | string[] | 可空 | 典型使用场景（「我什么时候该用它」） |
| `covers` | string[] | **至少 1 条** | 覆盖范围（能替你做什么） |
| `not_covers` | string[] | 可空 | 明确不做什么——比 `covers` 更能降低误用 |
| `capability_notes` | object | 可空；键、值都非空 | 能力名 → 一句话用途 |
| `constraints` | string[] | 可空 | 业务约束摘要（如 R4 / R5 / R6 的语义） |
| `paradigm_map` | object[] | **可选**；出现时非空，每行 `element` / `in_ontology` / `where` / `yours` 四列齐全且非空 | 范式要素对照表：本体要素 ↔ 你自己的系统（#111） |
| `examples` | object[] | 可空 | 示例题；六个必填子字段 + 一个可选子字段见下表 |
| `integrations` | string[] | 可空 | 接入说明（REST / MCP / OpenAPI） |

`examples[]` 的子字段：

| 子字段 | 类型 | 规则 | 说明 |
|---|---|---|---|
| `id` | string | 非空且唯一 | 题号（如 `T2-01`） |
| `question` | string | 非空 | 中文题干 |
| `capability` | string | 非空 | 能力名；框架**不校验**它是否在本包 `CAPABILITIES` 里 |
| `params` | object | 必填，可为 `{}` | 领域参数容器，原样透传给能力请求，框架不解析键 |
| `answer_hint` | string | 非空 | 期望答案的一句话 |
| `via` | string | 非空 | 走哪组规则（如 `R1 能力匹配`） |
| `group` | string | **可选**；出现时非空 | 展示分组（如 `看一次编排` / `预测一次变化`）；未声明的题归入「其余示例」，一个 group 都没有时保持平铺（#114） |
| `simulate` | object | **可选**；`edits` 非空 | 只读推演：每条 `{op: set\|add\|remove, subject, predicate, value, kind?: literal\|iri}` 都落在断言谓词上；页面在断言图副本上重推理并展示改动前后（#115） |
| `predict` | object | **可选**；四键 `prompt` / `options` / `answer` / `explain` 齐全，`options` ≥ 2，`answer` 必须是 `options` 之一 | 预测配对题：先猜 → 再跑 → 对错（#111） |

三条最容易踩的规则：

1. **必填槽位都要显式出现**：没有示例题写 `"examples": []`，没有能力说明写 `"capability_notes": {}`。漏写必填槽位是违约，不是"省略等于空"。可选槽位（`paradigm_map` / `examples[].predict` / `examples[].group` / `examples[].simulate`）相反：不需要时**省略整个键**，不要写成空数组 / 空对象 / 空字符串。
2. **包内禁止声明能否试跑**：不要写 `safe` / 类似字段；`safe` 只能由框架按运行态只读能力清单判定，未知字段会让整包加载失败。
3. **两种版本错误分开修**：`PLUGIN_API` 不认识 → 升级领域包或退回匹配的 SDK；`guide_version` 不认识 → 改 / 补 `guide.json`。两者都拒绝加载，但报错会指向不同修法。

最小合规样例（10 个槽位，空状态显式写出）：

```json
{
  "guide_version": "1",
  "display_name": "我的领域",
  "summary": "一句话说明这个领域能回答什么。",
  "scenarios": [],
  "covers": ["至少一条覆盖范围"],
  "not_covers": [],
  "capability_notes": {},
  "constraints": [],
  "examples": [],
  "integrations": []
}
```

### `GET /api/domains/current/guide` 响应结构

「当前领域」页只读这一个端点，响应刻意分三段：

| 顶层字段 | 说明 |
|---|---|
| `domain` / `display_name` / `imported` / `mode` / `loaded_at` / `guide_version` / `contract_ok` | 当前句柄（内部标识 + 展示名）、是否框架内置的「导入的本体」、领域 / 通用模式、加载时刻与契约校验结果 |
| `profile` | `guide.json` 的声明内容（人话部分，原样透出） |
| `runtime` | 框架按当前句柄实测：`query_kinds` / `apply_kinds` / `declared_capabilities` / `entity_schema` / `mcp` / `counts` / `rules` / `graph_groups` / `individuals` |
| `reconcile` | 声明与实测的对账：`notes_without_capability` / `capabilities_without_note` / `unavailable_examples` |
| `examples` | 加工后的示例题：题干 / 能力 / 参数 / `safe` / `reason` / `endpoint`；`safe` 由框架判定 |

> `profile` 回答「包说自己能做什么」，`runtime` 回答「框架实测它现在能做什么」，`reconcile` 回答「两边哪里对不上」。前端只渲染这三段，不自行判断能力可用性。

## 路径 C：加规则与查询类型

在现有领域上增量扩展，两条分支：

**加一条推理规则**

| 规则性质 | 做法 |
|---|---|
| OWL 能表达（属性链/传递/子类） | 加进本体公理，owlrl 自动推理，**零代码** |
| 关系若写成 OWL 公理会让 .owl 随个体膨胀（如 R2 复合委派：OWL 2 能表达，但为保持本体文件简洁改写规则层 SHACL 规则 `rules/*.ttl`），或本质是运行时校验（如 R4 合规冲突） | 推新结论的进规则层 `rules/*.ttl`；只做校验的在适配器加方法；两者的"为什么"文案都在 `derivation.json` 的 `derivations` 补对应 key |

**加一个查询类型**（三处联动）

1. 适配器加方法（返回 dict，可附 `derivation` 推导链）；
2. `derivation.json` 加对应 key（`expand` 按 key 查找展开文案）；
3. 出口注册：API 层加端点，或领域 `mcp.py` 的 `register_tools` 里加 `@server.tool`。

## 一条原则贯穿始终

> **本体管"是什么、能推出什么"，适配器管"业务怎么问"，配置管"说法怎么变"。三者分离，扩展才不用动核心。**

- **本体是唯一事实源**：类/个体/属性/中文名都在 .owl 里，配置不重复维护；
- **配置即行为**：改 `DEFAULT_CONFIG.update(...)` 就换了语义绑定，代码不动；
- **领域包自包含**：一个目录装下一个业务的全部，可插拔、可拷贝、可分享。

## 常见问题

- **Q：换本体后推理规则还能用吗？**
  A：公理结构保留即可——R3 传递闭包活在公理里，随本体一起换；R1 能力匹配与 R2 委派是规则层 `rules/*.ttl`（随领域包走、与本体解耦），R4 是适配器里的运行时校验。所以"同构本体"意味着两者都不用动。
- **Q：不想用 Python 技术栈怎么办？**
  A：本体本身是标准 RDF/OWL 文件，任何支持 OWL 的工具链（Protege、owlready2、任意图数据库）都能消费；本项目只是提供了一套开箱即用的服务层。架构思路（核心零领域词汇 + 领域包可插拔）与语言无关。

| 语法 | 作用 | 例子 | 对应的三元组 |
|---|---|---|---|
| `<rdf:RDF ... xmlns="...">` | 文件根 + 默认命名空间：文件里**不带前缀**的名字都归这个 IRI 管 | `xmlns="http://ontology.localhost/worker-job#"` | —（文件外壳） |

| 无前缀属性 `<p rdf:resource="#v"/>` | 给 x 加一条关系：x 的 p 属性取值 v（p 属于默认命名空间） | `<owns_skill rdf:resource="#Coding"/>` | `x p v` |
| 自闭合标签 `/>` | 没有内容的标签（只声明、不带属性说明） | `<owl:Class rdf:about="#Worker"/>` | —（写法） |
