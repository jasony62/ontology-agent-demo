# 06 用 MCP 把本体服务接入智能体
> 本文是《本体上手指南》系列第 7 篇（共 9 篇），零基础入门「本体 × 智能体」。

> 阅读时长：约 12 分钟 · 配套动手：约 8 分钟
> **读完你能**：把本体推理服务接进豆包，让它在对话里直接调用推理工具——"智能体 × 本体"正式合体

---

## MCP 是什么

**MCP（Model Context Protocol，模型上下文协议）** 是智能体的"工具协议"。一个类比：

> 电脑想用打印机，不需要认识每一台打印机的电路，只要接上 USB 接口、装好驱动。**MCP 就是智能体的 USB 接口**：任何能力，只要按 MCP 标准封装成"工具"，智能体就能自动发现、按说明调用。

具体到本项目：推理服务把自己封成一个 **MCP Server**，向智能体（豆包）暴露一份**工具清单**——每个工具带名称、参数说明、返回值结构。智能体在对话中"看到"这些工具，就知道"哦，我可以调用 capability_match 来回答谁能做任务"。

## 第 1 步：启动 MCP Server（Docker）

```bash
cd <项目根目录>
docker compose up -d mcp    # 容器内启动 MCP Server（:9000）
```

启动日志（实测）：

```
[info] 本体推理 MCP Server（agent_task）已启动（streamable-http，单进程双端点）: http://127.0.0.1:9000/mcp/ontology 与 /mcp/cq
```

> `docker compose up` 可同时起 API(:8000) 与 MCP(:9000)；单起 MCP 用 `docker compose up -d mcp`。compose 已配置容器内绑定 `0.0.0.0`，宿主机通过端口映射访问。

- **默认传输** `streamable-http`：供豆包连接器使用，本体推理地址 `http://127.0.0.1:9000/mcp/ontology`，CQ 集地址 `http://127.0.0.1:9000/mcp/cq`（旧地址 `/mcp` 仍指向本体推理）；
- **`--transport stdio`**：供本地 MCP 客户端（如 Claude Desktop）使用——stdio 需要标准输入输出通道，适合直接在宿主机运行 `python mcp/mcp_server.py --transport stdio`（需宿主机装有依赖）；
- **`--domain`** 指定领域，默认 `agent_task`，换领域换参数即可（篇 8）；
- 端口默认 **9000**——特意避开推理 API 的 8000，两者可同时运行；
- **内嵌引擎，零服务依赖**：MCP Server 自带引擎与本体，不需要先启动 REST API。

## 第 2 步：接入豆包（连接器）

豆包电脑版侧边栏操作：

1. 侧边栏「**技能 / 连接器**」→ 右上角「**添加**」→「**新建自定义连接器**」；
2. 传输类型选 **HTTP**，MCP 服务器 URL 填 `http://127.0.0.1:9000/mcp/ontology`（要管 CQ 集再加一个 `/mcp/cq` 连接器）；
3. 保存后即可在对话中直接调用本体推理工具。

> 连接器本质：把"对话中能看到哪些工具"告诉豆包。保存后豆包就"认识"了本体的 25 个工具（CQ 连接器另加 8 个）。

**怎么确认接上了？** 保存后直接问一句最轻的话，例如「登录模块开发谁能做？」——如果豆包调用到了本体工具（比如追问"为什么是他"能触发 `explain`），就说明接通了；如果没反应，先看容器日志 `docker compose logs mcp`，确认 `:9000` 起来、URL 没填错。

## 第 3 步：认识核心工具（完整清单见速查表 §C）

服务在同一进程内暴露两个端点，共 **35 个工具**：`/mcp/ontology` 25 个（领域业务 10 + 引擎通用 15）、`/mcp/cq` 10 个。按来源分：

- **领域业务工具 10 个**——随领域包注册（`capability_match`/`orchestrate`/`assign`/`classify`/`consistency`/`explain`/`ontology`/`entities`/`status`/`validate_shapes`），换领域这组跟着换；
- **引擎通用工具 15 个**——任意 `.owl` 可用（SPARQL、个体、类、类型、属性、重推理、证明、守卫、闸门、规则执行、合并预检等）；
- **CQ 工具 10 个**——框架级 `/mcp/cq`，不依赖领域包，导入裸 OWL 也可用（集读写 / 单题增删 / 依据定位 / 批量质检 / 出题 / TBox 校验 / 回归 / 审计）。

入门只需掌握 **3 个核心工具**（完整 35 个清单与参数见文末《附录-速查表》§C）：

| 工具 | 说明 |
|---|---|
| `capability_match` | **主线**：R1/R2 能力匹配——哪些智能体可执行该任务，附推导链 |
| `orchestrate` | **主线**：R3 任务编排——拆解依赖链、拓扑排序、逐环节匹配执行者 |
| `entities` | **选参助手**：返回全部任务/智能体/能力/约束的短名与中文标签，不确定参数时先查它，避免瞎猜短名 |

> 两点提前知道：
> - `query_sparql` 等部分通用工具**受领域语义白名单控制**：默认 `agent_task` 领域启用了白名单，此时裸 SPARQL 会被拦（返回 `denied`），应改用受控的 `run_predefined_query`（见速查附录）。
> - 完整工具清单始终以 MCP `tools/list` 返回为准。

## 第 4 步：对话演示完整链路

接入后，在豆包里直接问：

> **「登录模块开发谁能做？」**

完整链路（配图如下）：

![MCP 接入：把本体服务变成智能体的"工具"](assets/06-mcp-arch.png)

1. **豆包听懂问题**：识别出这是"找任务执行者"的意图；
2. **调用工具**：`capability_match(task="t_login_dev")`；
3. **本体推理**：R1 能力覆盖匹配（规则层），生成 `matches` 与推导链。

**在当前默认数据下，实际返回的是空态**：

```json
{
  "task": "t_login_dev",
  "task_label": "登录模块开发",
  "requires_capabilities": ["编码实现"],
  "matches": [],
  "derivation": [{ "kind": "rule", "content": "匹配完成：无可执行该任务的 Agent（可补充能力或人工介入）" }]
}
```

这正好演示了能力匹配的一个关键依赖：**任务要求的「编码实现」（中文标签）与 Agent 的 `has_capability=Coding`（英文短名）是同一能力、但两种写法没有对齐，所以匹配为空**。要让匹配成功，需要把能力标识统一（任务与智能体用同一种写法）——这就是"规范能力标识"的意义。

编排场景同理：

> **「新功能上线怎么安排？」**

豆包会调用 `orchestrate(task="t_feature")`，在当前数据下同样返回空步骤（`steps: []`），需要先把复合任务的子任务拆解与能力标识补齐。接入后第一件事，往往是**对照实际返回**调整能力/依赖数据，而不是照文档的示意结果来预期。

## 与 REST API 的关系

| | REST API（:8000） | MCP Server（:9000） |
|---|---|---|
| 面向 | 前端页面、脚本、任何 HTTP 客户端 | 智能体（豆包连接器等 MCP 客户端） |
| 协议 | HTTP + JSON | MCP（JSON-RPC / SSE） |
| 工具/端点 | 45 个端点 | 35 个工具（本体 25 + CQ 10） |
| 依赖 | 独立进程 | 内嵌引擎，不依赖 REST |

两者共享**同一套引擎与领域包**——这就是篇 5（搭建本体推理服务）所讲的服务"多通道出口"：**同一种能力，按消费方选通道**。脚本和前端走 REST；智能体走 MCP。

## 小结

1. **MCP = 智能体的 USB 接口**：能力封装成标准工具，智能体自动发现、按说明调用。
2. **一行命令启动**：`docker compose up -d mcp`，内嵌引擎零依赖；豆包侧边栏加连接器即可接入。
3. **35 个工具**：10 个领域业务工具 + 15 个引擎通用工具（`/mcp/ontology`）+ 10 个框架级 CQ 工具（`/mcp/cq`）；入门先掌握 `capability_match` / `orchestrate` / `entities`。
4. **智能体听懂人话，本体算得准讲得清**——MCP 是两者的"合体通道"。

**常见问题**

- **Q：MCP 和 REST 到底差在哪？**
  A：REST 是"人/程序按文档调用"；MCP 是"智能体自动发现并调用"——工具带机器可读的 schema 和描述，智能体自己决定何时调用哪个。对本项目而言，二者背后是同一个引擎。
- **Q：只能接豆包吗？**
  A：不是。任何 MCP 客户端都能接：`--transport stdio` 可接本地客户端 / Claude Desktop；streamable-http 可接其他支持 MCP 的智能体平台。
